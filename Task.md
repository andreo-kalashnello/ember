Нужно реализовать полноценный production-ready лендинг на основе приложенных дизайн-референсов.

Проект:
Амбер

Тип сайта:
РЕСТОРАН

Используй приложенные изображения как основной источник правды по дизайну.

Среди приложенных файлов есть:


1. Отдельные screenshots каждой секции.
   Они определяют:
   - точную композицию блока;
   - изображения;
   - тексты;
   - пропорции;
   - размеры элементов;
   - типографику;
   - цвета;
   - границы;
   - кнопки;
   - иконки;
   - внутренние отступы;
   - декоративные элементы.

При конфликте между общим скрином и отдельным скрином секции:
- используй общий скрин для порядка и высоты секций;
- используй отдельный скрин секции для деталей и визуальной точности.

ВАЖНО

Не вставляй приложенные скриншоты как цельные изображения или фон страницы.

Нужно воссоздать настоящий сайт:
- отдельные HTML-элементы;
- настоящие тексты;
- настоящие кнопки;
- настоящие формы;
- настоящая навигация;
- отдельные изображения;
- полноценный responsive layout.

Скриншоты используются только как дизайн-референсы.

────────────────────────────────────
ПЕРЕД НАЧАЛОМ
────────────────────────────────────

1. Изучи текущий репозиторий.
2. Проверь package.json и существующие зависимости.
3. Найди все приложенные дизайн-референсы и ассеты.
4. Определи:
   - количество секций;
   - порядок секций;
   - повторяющиеся UI-паттерны;
   - палитру;
   - типографику;
   - размеры контейнера;
   - необходимые изображения;
   - интерактивные элементы.
5. Составь короткий план реализации.
6. Только после анализа начинай изменять файлы.

Не задавай вопросы, если ответ можно достоверно определить по скриншотам или структуре проекта.

Если какой-то элемент невозможно однозначно определить, выбери наиболее логичную реализацию, сохрани общую стилистику и укажи допущение в итоговом отчёте.

────────────────────────────────────
ТЕХНОЛОГИИ
────────────────────────────────────

Используй текущий стек проекта.

Если проект создаётся с нуля, используй:

- Next.js
- React
- TypeScript
- Tailwind CSS
- next/image
- Lucide React
- Redux, zustand
- Framer Motion только для оправданных анимаций

Для форм при необходимости:

- React Hook Form
- Zod

Не добавляй:
- Redux;
- отдельный сложный backend;
- глобальный state manager;
- тяжёлые UI-библиотеки;
- лишние зависимости;

если они объективно не нужны для этого лендинга.

────────────────────────────────────
АРХИТЕКТУРА
────────────────────────────────────

Разбей страницу на понятные компоненты.

Пример:

- Header
- HeroSection
- InfoBar
- FeaturedSection
- AboutSection
- ServicesSection
- GallerySection
- TestimonialsSection
- ReservationSection
- Footer

Названия компонентов должны отражать реальный смысл секций проекта.

Повторяющиеся элементы вынеси в переиспользуемые компоненты:

- Button
- SectionHeading
- NavigationLink
- ImageCard
- ReviewCard
- FormField
- IconBadge
- StatItem

Не создавай:
- один огромный page-компонент;
- сотни слишком мелких компонентов;
- ненужный prop drilling;
- чрезмерную абстракцию;
- универсальный компонент с десятками условных props.

Данные для карточек, меню, отзывов или услуг храни в типизированных массивах, а не копируй JSX вручную.

────────────────────────────────────
ВИЗУАЛЬНАЯ ТОЧНОСТЬ
────────────────────────────────────

Максимально точно повтори дизайн референсов.

Сохрани:

- порядок секций;
- композицию;
- ширину контейнера;
- высоту блоков;
- внешние и внутренние отступы;
- колонки;
- размеры изображений;
- пропорции карточек;
- позиционирование текста;
- визуальную иерархию;
- цвета;
- границы;
- радиусы;
- тени;
- фоновые изображения;
- декоративные линии;
- иконки;
- кнопки;
- типографику;
- контраст;
- общее настроение дизайна.

Не упрощай сложные секции до обычной сетки карточек.

Не делай все секции одинаковыми.

Не меняй композицию на своё усмотрение.

Не добавляй новые блоки, которых нет в дизайне.

Не убирай существующие блоки.

Не делай дизайн «более современным» или «более удобным», если это меняет референс.

Используй точные тексты со скриншотов, когда они читаемы.

Не используй lorem ipsum.

────────────────────────────────────
РАЗМЕРЫ И КОНТЕЙНЕРЫ
────────────────────────────────────

Основной desktop viewport:
1440 px.

Определи реальную ширину внутреннего контейнера по дизайну.

Когда её нельзя достоверно определить, используй:

- desktop frame: 1440 px;
- maximum content width: 1200–1312 px;
- центрированный контейнер;
- безопасные горизонтальные поля;
- без прилипания контента к краям.

Full-width фоны и фоновые изображения могут занимать всю ширину viewport.

Основной текст, карточки, формы и навигация должны находиться внутри общего контейнера.

Не допускай:
- горизонтальный overflow;
- выход элементов за границы страницы;
- случайное обрезание текста;
- наложение секций;
- слишком узкий сайт внутри 1440 px;
- разную ширину контейнера без причины.

────────────────────────────────────
ИЗОБРАЖЕНИЯ
────────────────────────────────────

Не используй full-page screenshot как изображение сайта.

Для каждого визуального блока:

1. Найди подходящий отдельный ассет среди приложенных файлов.
2. Если отдельного ассета нет, аккуратно извлеки изображение из качественного screenshot секции или используй предоставленное оригинальное изображение.
3. Сохрани изображения локально в public/images.
4. Дай файлам понятные названия.
5. Используй next/image.
6. Настрой корректные:
   - width;
   - height;
   - sizes;
   - object-fit;
   - object-position;
   - priority для hero;
   - lazy loading для остальных изображений.

Не используй случайные внешние ссылки.

Не растягивай изображения.

Не изменяй пропорции фотографий.

Не ухудшай качество изображений без необходимости.

Если изображение содержит текст интерфейса, не используй его как готовый UI — интерфейс должен быть реализован HTML/CSS.

────────────────────────────────────
ТИПОГРАФИКА
────────────────────────────────────

Определи шрифтовую пару по дизайну.

Когда точный шрифт неизвестен:
- подбери максимально близкий Google Font или системный аналог;
- используй serif для редакционных заголовков, если это соответствует референсу;
- используй читаемый sans-serif для интерфейса и основного текста.

Соблюдай:
- размеры;
- line-height;
- letter-spacing;
- font-weight;
- регистр;
- максимальную ширину текстовых блоков;
- переносы строк из дизайна.

Не уменьшай текст только ради того, чтобы он поместился.

Сначала исправляй ширину контейнера, колонки и spacing.

────────────────────────────────────
ИНТЕРАКТИВНОСТЬ
────────────────────────────────────

Реализуй настоящую интерактивность там, где она подразумевается дизайном:

- навигационные ссылки;
- плавный переход к секциям;
- мобильное меню;
- hover-состояния;
- focus-состояния;
- кнопки;
- категории и фильтры;
- слайдеры;
- карусели;
- стрелки навигации;
- dropdown-поля;
- формы;
- состояния loading, success и error.

Не оставляй декоративные кнопки полностью неработающими.

Если backend пока не подключён:
- реализуй клиентскую форму;
- добавь валидацию;
- добавь mock-success state;
- подготовь понятную точку подключения API;
- не отправляй данные на случайные сервисы.

Анимации должны быть лёгкими:

- появление при прокрутке;
- мягкий hover;
- небольшой zoom изображений;
- плавные dropdown;
- переходы меню;
- аккуратная карусель.

Учитывай prefers-reduced-motion.

Не перегружай страницу анимациями.

────────────────────────────────────
АДАПТИВНОСТЬ
────────────────────────────────────

Создай один responsive сайт, а не отдельные несвязанные версии.

Обязательно проверь:

- 1440 px;
- 1280 px;
- 1024 px;
- 768 px;
- 390 px.

На desktop максимально точно повтори дизайн.

На tablet:
- корректно перестрой сложные композиции;
- сохрани визуальную иерархию;
- не уменьшай всё пропорционально до нечитаемого размера.

На mobile:
- перестрой многоколоночные секции в одну или две колонки;
- сделай полноценное мобильное меню;
- сохрани разумные поля;
- увеличь интерактивные зоны;
- обеспечь читаемость текста;
- не допускай горизонтальный overflow;
- сохрани важные изображения;
- скрывай только второстепенный декор.

Минимальный размер интерактивной области:
примерно 44 × 44 px.

────────────────────────────────────
ДОСТУПНОСТЬ И КАЧЕСТВО
────────────────────────────────────

Используй semantic HTML:

- header;
- nav;
- main;
- section;
- article;
- form;
- footer.

Добавь:
- alt для изображений;
- label для полей;
- aria-label для кнопок с иконками;
- keyboard navigation;
- видимые focus-состояния;
- достаточный цветовой контраст.

Не допускай:
- пустых href;
- вложенных интерактивных элементов;
- дублирующихся id;
- console errors;
- hydration errors;
- битых изображений;
- layout shift из-за отсутствующих размеров изображений.

────────────────────────────────────
ЭТАПЫ РАБОТЫ
────────────────────────────────────

Работай последовательно.

Этап 1:
- проанализируй все screenshots;
- сопоставь секции;
- создай структуру компонентов;
- настрой глобальные стили, шрифты, цвета и контейнер.

Этап 2:
- реализуй header и hero;
- сравни с референсом;
- исправь основные размеры.

Этап 3:
- последовательно реализуй все секции сверху вниз;
- после каждого крупного блока проверяй визуальное соответствие.

Этап 4:
- реализуй footer;
- добавь интерактивность;
- добавь адаптив.

Этап 5:
- проведи полный технический и визуальный QA.

Не прекращай выполнение после первых двух или трёх секций.

Реализуй всю страницу от header до footer.

────────────────────────────────────
ПРОВЕРКА
────────────────────────────────────

После реализации:

1. Запусти lint.
2. Запусти TypeScript-проверку.
3. Запусти production build.
4. Исправь все ошибки.
5. Запусти сайт локально.
6. Используй Playwright или доступный браузерный инструмент.
7. Сделай screenshots страницы на:
   - 1440 px;
   - 1024 px;
   - 768 px;
   - 390 px.
8. Сравни desktop screenshot с приложенным full-page reference.
9. Сравни каждую секцию с отдельным screenshot.
10. Исправь объективные расхождения.
11. Повторно запусти проверки.

Особенно проверь:

- ширину контейнера;
- отступы по бокам;
- высоту hero;
- размеры заголовков;
- переносы текста;
- размеры карточек;
- кадрирование изображений;
- переходы между секциями;
- мобильное меню;
- формы;
- карусели;
- отсутствие overflow;
- console errors;
- работу всех кнопок.

Не выполняй git push, merge или production deploy без отдельного подтверждения.
